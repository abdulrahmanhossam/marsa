## 1. أساسيات النشر <a id="deployment-basics"></a>

### منصة النشر — Deployment Platform <a id="platform"></a>

برنامج يدير تحويل الكود إلى تطبيق يعمل: يبني، يشغّل، يوجّه، يراقب، ويسمح بالتراجع. مرسى منصة نشر ذاتية الاستضافة، وليس لغة برمجة أو محرك حاويات.

**في مرسى:** الطبقة التي تربط Git وDocker وCaddy وPostgreSQL، وتعرض الحالة للمستخدم.

### الاستضافة الذاتية — Self-hosted <a id="self-hosted"></a>

أن تشغّل البرنامج على خادم تملكه أو تستأجره، بدل أن تستخدم خدمة سحابية يديرها مزوّد. أنت مسؤول عن التثبيت والنسخ الاحتياطي والترقية.

**في مرسى:** الخادم والبيانات والأسرار تبقى تحت سيطرتك، لكن المسؤولية التشغيلية تبقى عليك أيضًا.

### منصة كخدمة — PaaS <a id="paas"></a>

اختصار Platform as a Service: منصة تدير النشر والتشغيل نيابة عنك. بعضها سحابي، وبعضها ذاتي الاستضافة مثل Coolify وDokku.

**في مرسى:** يقدّم تجربة قريبة من PaaS على خادم واحد، لكنه لا يعد بكل ميزات المنصات السحابية.

### المنتج الأدنى القابل للتطبيق — MVP <a id="mvp"></a>

أصغر نسخة تحقق قيمة حقيقية للمستخدم، وليس نسخة ناقصة من المنتج النهائي. الهدف هو تعلّم أسرع وبناء أساس يمكن توسيعه.

**في مرسى:** 0.1 هي MVP: خادم واحد، خدمة واحدة، Docker، PostgreSQL، Caddy، واجهة وCLI وAPI.

### النشر — Deployment <a id="deployment"></a>

محاولة تحويل إصدار من الكود إلى تطبيق يعمل. لها سجل وحالة وخطوات وسجلات ونتيجة.

**في مرسى:** النشر كائن دائم في قاعدة البيانات، وليس مجرد أمر في الذاكرة. يمكن أن يفشل دون أن يتأثر الإصدار الذي يخدم.

### الإصدار — Release <a id="release"></a>

النتيجة الناجحة للنشر: صورة محددة تعمل وتخدم الحركة. الإصدار ليس الملفات على جهازك، بل مرجع ثابت إلى صورة وبصمة.

**في مرسى:** الإصدارات لا تُعدّل في مكانها؛ التغيير ينشئ إصدارًا جديدًا.

### المشروع — Project <a id="project"></a>

وحدة تنظيم للتطبيق الذي تديره. يحتوي عادةً على إعدادات المصدر والبناء والنطاق.

**في مرسى 0.1:** مشروع واحد له بيئة واحدة وخدمة واحدة.

### البيئة — Environment <a id="environment"></a>

سياق تشغيل مثل الإنتاج أو التجربة. تفصل الإعدادات والإصدارات والمسارات.

**في مرسى 0.1:** بيئة واحدة لكل مشروع، مع بقاء الحقل `environment` في التصميم لتوسعة مستقبلية.

### الخدمة — Service <a id="service"></a>

العملية القابلة للنشر داخل المشروع، مثل تطبيق ويب. قد يحتاج المشروع الحقيقي إلى عدة خدمات، لكن ذلك خارج نطاق 0.1.

**في مرسى:** خدمة واحدة لكل نشر، وهذا يبسّط اللقطة والشبكة والتوجيه.

### اللقطة — Snapshot <a id="snapshot"></a>

نسخة مجمّدة من كل ما يحتاجه النشر: الالتزام، خطة البناء، المنفذ، مسار الصحة، ومراجع الأسرار. لا تتغير بعد القبول.

**في مرسى:** تضمن أن تعديل المشروع أثناء النشر لا يغيّر النشر الجاري.

### غير قابل للتغيير — Immutable <a id="immutable"></a>

شيء لا يُعدّل بعد إنشائه؛ أي تغيير ينتج نسخة جديدة. في مرسى: اللقطة، الإصدار، وصورة الحاوية.

**لماذا:** يجعل التاريخ صادقًا والتراجع ممكنًا.

### القبول — Admission <a id="admission"></a>

المرحلة التي يقرر فيها النظام قبول طلب النشر وإنشاء سجله. تتحقق من الصلاحيات، ومن عدم وجود نشر نشط، وتجمّد اللقطة.

**في مرسى:** يتم القبول داخل معاملة قاعدة بيانات مع قفل صف البيئة.

### الفحص الصحي — Health Check <a id="health-check"></a>

طلب متكرر إلى التطبيق للتأكد من أنه يعمل ومستعد لاستقبال الحركة. قد يكون HTTP أو TCP.

**في مرسى:** لا يوجّه النطاق إلى الإصدار الجديد حتى تنجح الفحوص وتستقر.

### التراجع — Rollback <a id="rollback"></a>

العودة إلى إصدار سابق. في مرسى ليس تعديلًا للتاريخ، بل **نشر جديد** يشير إلى صورة قديمة محددة ويمر بنفس فحص الصحة.

**لماذا:** يحافظ على سجل التدقيق ويمنع حالات غامضة.

### يتطلب إجراء — Action Required <a id="action-required"></a>

حالة نهائية تعني أن النظام توقف بأمان لكنه يحتاج قرارًا بشريًا. عادةً يكون الإصدار السابق ما زال يخدم.

**في مرسى:** تظهر عند فشل فحص الصحة أو التوجيه مع وجود إصدار سابق.

### نجح مع تحذيرات — Succeeded with Warnings <a id="succeeded-with-warnings"></a>

حالة نجاح غير كامل: التطبيق يعمل والمسار فعّال، لكن هناك مشكلة غير قاتلة مثل شهادة TLS معلقة.

**في مرسى:** لا تُخلط مع الفشل، ولا تُخفى؛ التحذير يظهر للمستخدم.

### آلة الحالة — State Machine <a id="state-machine"></a>

نموذج يحدد الحالات الممكنة والانتقالات المسموحة بينها. يمنع الانتقالات غير المنطقية.

**في مرسى:** حالة النشر لا ترجع للوراء، والحالات النهائية لا تتغير.

### التسوية — Reconciliation <a id="reconciliation"></a>

مقارنة الحالة المرغوبة في قاعدة البيانات مع الواقع في Docker وCaddy، ثم إصلاح الفرق بأمان.

**في مرسى:** تُصلح فقط الموارد التي تحمل علامات `io.marsa.*`، ولا تلمس الموارد الأجنبية.

### الإلغاء — Cancellation <a id="cancellation"></a>

إيقاف نشر في نقطة آمنة. لا يعني حذف التاريخ، بل إنهاء المحاولة مع تنظيف ما أُنشئ.

**في مرسى:** مسموح من `queued` حتى `health_checking`، وغير مسموح أثناء `routing`.

### الإصدار السابق — Previous Release <a id="previous-release"></a>

الإصدار الذي يخدم الحركة قبل النشر الجديد. يبقى محفوظًا حتى يثبت الجديد، ويُستخدم للتراجع.

**في مرسى:** لا يُوقف لمجرد بدء بناء جديد.

### مستوى التحكم — Control Plane <a id="control-plane"></a>

الجزء الذي يدير النظام ويتخذ القرارات: الواجهة، API، قاعدة البيانات، والعامل. لا يخدم حركة تطبيقات المستخدمين.

**في مرسى:** انهيار مستوى التحكم لا يجب أن يوقف التطبيقات التي تعمل بالفعل ومساراتها مثبتة في Caddy.

### المضيف — Host <a id="host"></a>

الجهاز أو نظام التشغيل الذي تعمل عليه الحاويات وخدمات مرسى. في 0.1 هو خادم Linux واحد.

**في مرسى:** المضيف مخصص لمرسى؛ لا تشاركه مع خدمات غير موثوقة.

### الطابور — Queue <a id="queue"></a>

قائمة أعمال تنتظر التنفيذ، مرتبة حسب الأولوية أو وقت الإنشاء.

**في مرسى:** طابور النشر محفوظ في PostgreSQL، وليس في ذاكرة العملية.

### خطة البناء — Build Plan <a id="build-plan"></a>

وصف قابل للتكرار لكيفية بناء التطبيق: نوع المشروع، صورة الأساس، الأوامر، المنفذ، ومسار الصحة.

**في مرسى:** تُكتشف أو تُعلن في `marsa.json`، وتُجمَّد داخل اللقطة قبل النشر.

### القطع — Cutover <a id="cutover"></a>

لحظة تحويل الحركة من الإصدار القديم إلى الجديد بعد نجاح فحص الصحة.

**في مرسى:** لا يحدث القطع قبل النجاح، والمسار القديم يبقى حتى تأكيد الجديد.

### Docker Compose <a id="compose"></a>

أداة لتعريف وتشغيل عدة حاويات وخدمات معًا من ملف YAML.

**في مرسى:** غير مدعوم في 0.1؛ المشروع يدير خدمة واحدة لكل نشر.

### Kubernetes <a id="kubernetes"></a>

منصة لتنسيق الحاويات على مجموعة خوادم، مع موازنة حمل واستعادة تلقائية.

**في مرسى:** ليس بديلًا لـKubernetes ولا يحاول محاكاته؛ النطاق خادم واحد.

### MCP <a id="mcp"></a>

اختصار Model Context Protocol: بروتوكول يسمح لوكلاء الذكاء الاصطناعي باستدعاء أدوات وخدمات.

**في مرسى:** واجهات MCP وتغيير الإنتاج بالوكيل مؤجلة خارج 0.1.

## 2. Git والمصادر <a id="git-sources"></a>

### Git <a id="git"></a>

نظام لإدارة تاريخ الملفات والتغييرات. يسجّل من غيّر ماذا، ويسمح بفروع ودمج وعودة إلى نسخة سابقة.

**في مرسى:** مصدر الحقيقة للكود الذي سيُبنى؛ لا يُبنى من مجلد عشوائي على الخادم.

### المستودع — Repository <a id="repository"></a>

مكان يحتوي ملفات المشروع وتاريخ Git. قد يكون محليًا أو على GitHub/GitLab أو خادم Git عام.

**في مرسى:** يربط المشروع بمستودع عبر HTTPS، ويرفض `ssh://` و`file://` والمسارات المحلية في 0.1.

### الالتزام — Commit <a id="commit"></a>

لقطة من التغييرات لها معرّف فريد ورسالة. النشر يستخدم التزامًا محددًا، لا „آخر ملفات“ غامضة.

**في مرسى:** يُسجَّل معرّف الالتزام في اللقطة، ويُستخدم لإعادة البناء عند الحاجة.

### الفرع — Branch <a id="branch"></a>

خط تطوير مستقل داخل المستودع، مثل `main` أو `feature/login`. يمكن دمج الفروع لاحقًا.

**في مرسى:** يختار المستخدم الفرع، ويمكن للـ webhook أن يستمع لفرع محدد فقط.

### الدفع — Push <a id="push"></a>

إرسال التزامات محلية إلى مستودع بعيد. في سياق مرسى، هو غالبًا الحدث الذي يبدأ النشر.

**مثال:** `git push origin main`.

### مزوّد Git — Git Provider <a id="git-provider"></a>

خدمة تستضيف المستودعات، مثل GitHub أو GitLab. قد ترسل webhooks وتتطلب رموز وصول للمستودعات الخاصة.

**في مرسى:** GitHub وGitLab وGit عبر HTTPS مدعومة في 0.1.

### Webhook <a id="webhook"></a>

طلب HTTP يرسله مزوّد Git إلى مرسى عند حدث، مثل push. يسمح بالبدء التلقائي للنشر.

**في مرسى:** يجب التحقق من توقيعه، ومنع إعادة إرساله، وتصفية الفرع.

### توقيع HMAC <a id="hmac"></a>

طريقة للتحقق من أن رسالة لم تُعدّل ومن أن مرسلها يعرف مفتاحًا سريًا. تُحسب بصمة للجسم الخام باستخدام المفتاح.

**في مرسى:** يُقارن التوقيع بزمن ثابت، ويُرفض التوقيع الخاطئ قبل تحليل JSON.

### معرّف التسليم — Delivery ID <a id="delivery-id"></a>

معرّف يرسله مزوّد Git لكل تسليم webhook. يُستخدم لمنع معالجة نفس الحدث مرتين.

**في مرسى:** `(provider, delivery_id)` هو حد التكرار.

### رمز الوصول الشخصي — PAT <a id="pat"></a>

اختصار Personal Access Token: رمز طويل يستخدمه المستخدم أو أداة للوصول إلى API أو خدمة، بدل كلمة المرور. توجد أنواع مختلفة، ولا يجوز الخلط بينها.

**في مرسى:** يوجد نوعان:
- **رمز مرسى الشخصي (Marsa PAT):** يبدأ بـ `marsa_pat_`، يُستخدم للـAPI وCLI، ويُخزَّن كبصمة hash ويُعرض مرة واحدة.
- **رمز مزوّد Git:** رمز من GitHub أو GitLab للوصول إلى مستودع خاص، ويُشفَّر كبيانات اعتماد للمصدر.

### رمز مزوّد Git — Git Provider Token <a id="git-provider-token"></a>

بيانات اعتماد يصدرها GitHub أو GitLab أو مزوّد آخر، وتُستخدم لقراءة مستودع خاص أو استدعاء API الخاص به.

**في مرسى:** يُشفَّر عند التخزين، ولا يُعاد من API. رفضه يعطي `source.auth_failed`. لا تستخدم رمز مرسى الشخصي مكانه.

### مستودع خاص — Private Repository <a id="private-repository"></a>

مستودع لا يستطيع الجميع قراءته. يحتاج النشر إلى بيانات اعتماد مشفرة.

**في مرسى:** تُشفَّر بيانات الاعتماد ولا تُعاد من API.

### SSRF <a id="ssrf"></a>

اختصار Server-Side Request Forgery: استغلال خادم ليجعل طلبات إلى عناوين داخلية أو حساسة. يحدث عندما يقبل الخادم عنوان URL من المستخدم دون تحقق.

**في مرسى:** روابط المستودعات والتحويلات تُفحص لمنع الوصول إلى العناوين الخاصة أو المحلية.

## 3. البناء والحاويات <a id="build-containers"></a>

### Docker <a id="docker"></a>

منصة لبناء وتشغيل التطبيقات داخل حاويات. تعزل العملية عن بقية النظام إلى حد كبير، لكنها ليست حدود أمان مطلقة.

**في مرسى:** محرك البناء والتشغيل الوحيد في 0.1.

### الصورة — Image <a id="image"></a>

قالب ثابت يحتوي ملفات التطبيق وبيئة التشغيل والتعليمات. لا تتغير بعد بنائها؛ لها بصمة (Digest).

**في مرسى:** البناء ينتج صورة، والنشر يشير إليها بالبصمة.

### الحاوية — Container <a id="container"></a>

نسخة قابلة للتشغيل من صورة. لها عملية وشبكة وموارد، ويمكن إنشاؤها وحذفها دون تغيير الصورة.

**في مرسى:** كل إصدار يعمل داخل حاوية واحدة في 0.1.

### Dockerfile <a id="dockerfile"></a>

ملف يصف خطوات بناء صورة: صورة الأساس، نسخ الملفات، الأوامر، المنفذ، وأمر التشغيل.

**في مرسى:** يمكن أن يكون مصدر خطة البناء عندما لا يكفي الاكتشاف التلقائي. تذكّر أن Dockerfile غير الموثوق يعني تنفيذ كود.

### البناء — Build <a id="build"></a>

عملية تحويل الكود إلى صورة قابلة للتشغيل. تشمل جلب الاعتماديات، الترجمة أو التجميع، ونسخ الناتج.

**في مرسى:** يجري داخل Docker مع حدود موارد، وتُلتقط سجلاته وتُنقّى من الأسرار.

### سياق البناء — Build Context <a id="build-context"></a>

الملفات التي تُرسل إلى محرك البناء. يجب أن تكون محدودة وآمنة، وألا تتضمن `.git` أو مسارات خارجة.

**في مرسى:** يُصدَّر الالتزام إلى مساحة خاصة، وتُمنع المسارات المتسللة والروابط الرمزية الخارجة.

### BuildKit <a id="buildkit"></a>

محرك بناء حديث في Docker يدعم التخزين المؤقت، والأسرار، والبناء المتوازي. يُستخدم عندما يكون متاحًا.

**في مرسى:** تُمرَّر أسرار البناء كـ BuildKit secrets، لا كوسائط أو متغيرات بيئة.

### OCI <a id="oci"></a>

اختصار Open Container Initiative: معايير لصيغة الصور وسجلاتها. تجعل الصور قابلة للنقل بين الأدوات.

**في مرسى:** يمكن نشر صورة OCI جاهزة بدل بناء من كود.

### سجل الصور — Registry <a id="registry"></a>

خدمة تخزّن الصور وتوزّعها، مثل Docker Hub أو GHCR. قد تكون عامة أو خاصة.

**في مرسى:** يسحب الصور الأساسية والصور الجاهزة، ويُفضّل التثبيت بالبصمة.

### السحب — Pull <a id="pull"></a>

تنزيل صورة من سجل الصور إلى الخادم قبل تشغيلها.

**في مرسى:** الصورة الجاهزة تُسحب عند النشر. إذا كان المرجع وسمًا، يُحوَّل إلى بصمة ويُسجَّل، حتى لا يتغير الإصدار لاحقًا.

### الوسم — Tag <a id="tag"></a>

اسم مقروء لصورة، مثل `v1.2` أو `latest`. قد يتغير، لذلك لا يكفي وحده للتراجع الدقيق.

**في مرسى:** عند استخدام صورة جاهزة، يُحوَّل الوسم إلى بصمة عند النشر.

### البصمة — Digest <a id="digest"></a>

معرّف فريد يعتمد على محتوى الصورة، مثل `sha256:...`. لا يتغير إذا لم يتغير المحتوى.

**في مرسى:** الإصدار والتراجع يشيران إلى البصمة، لا إلى الوسم فقط.

### ذاكرة البناء — Build Cache <a id="build-cache"></a>

نتائج وسيطة يُعاد استخدامها لتسريع البناء. يجب تقييدها وتنظيفها حتى لا تستهلك القرص.

**في مرسى:** نفس الالتزام ونفس الخطة قد يعيدان استخدام الصورة، ما لم يُطلب بناء قسري.

### سياسة الاحتفاظ بالصور — Image Retention <a id="image-retention"></a>

قواعد تحدد متى تُحذف الصور القديمة. يجب ألا تحذف صورة يستخدمها إصدار نشط أو إصدار معروف أنه سليم.

**في مرسى:** الاحتفاظ الافتراضي يحمي النشط والسابق وآخر نسخة سليمة.

### مساحة العمل — Workspace <a id="workspace"></a>

مجلد مؤقت خاص بنشر واحد. يُنشأ من الالتزام، ويُحذف بعد الانتهاء أو الفشل.

**في مرسى:** لا تُشارك مساحات العمل بين النشرات.

### بناء متعدد المعماريات — Multi-arch <a id="multi-arch"></a>

بناء صور تعمل على معماريات مختلفة مثل `amd64` و`arm64`.

**في مرسى:** مخرج الإصدار يستهدف المعماريتين.

## 4. الشبكة والحافة <a id="network-edge"></a>

### Caddy <a id="caddy"></a>

خادم ويب ووكيل عكسي يدير HTTPS تلقائيًا. في مرسى هو الحافة العامة الوحيدة.

**في مرسى:** يستقبل 80/443، يحصل على الشهادات، ويوجّه النطاقات إلى الحاويات.

### الوكيل العكسي — Reverse Proxy <a id="reverse-proxy"></a>

خادم يقف أمام التطبيقات، يستقبل طلبات المستخدمين ويوجّهها إلى التطبيق المناسب. يخفي التفاصيل الداخلية ويدير TLS.

**في مرسى:** Caddy هو الوكيل العكسي الوحيد.

### المصب — Upstream <a id="upstream"></a>

الخدمة التي يوجّه إليها الوكيل العكسي الطلب، مثل حاوية تطبيق على منفذ داخلي.

**في مرسى:** لا ينشر التطبيق منفذًا على المضيف؛ Caddy يصل إليه عبر شبكة المشروع.

### المسار — Route <a id="route"></a>

قاعدة تربط اسم نطاق أو مسارًا بخدمة. قد تتضمن شهادة وتوجيه HTTP إلى HTTPS.

**في مرسى:** تُدار المسارات كمجموعة كاملة، وتُطبّق فقط بعد نجاح الفحص.

### اسم المضيف — Hostname <a id="hostname"></a>

اسم يستخدمه المتصفح للوصول إلى خدمة، مثل `app.example.com`. ليس كل اسم مضيف اسم نطاق مؤهل بالكامل.

**في مرسى:** يُطبَّع إلى أحرف صغيرة، ويُرفض wildcard وIP والمنفذ والمسارات في 0.1.

### اسم النطاق المؤهل — FQDN <a id="fqdn"></a>

اسم نطاق كامل يحدد موقعًا على الإنترنت، مثل `app.example.com`.

**في مرسى:** التحقق يستخدم FQDN صالحًا وخاليًا من wildcard.

### DNS <a id="dns"></a>

نظام يحوّل أسماء النطاقات إلى عناوين IP أو سجلات أخرى. بدون DNS صحيح، لن يصل المستخدم إلى خادمك.

**في مرسى:** يظهر للمستخدم سجل TXT أو CNAME مطلوب للتحقق.

### سجل TXT <a id="txt-record"></a>

سجل DNS نصي يُستخدم غالبًا لإثبات ملكية النطاق أو التحقق من إعداد.

**في مرسى:** قد يُطلب سجل TXT محدد للتحقق من ملكية اسم النطاق.

### سجل CNAME <a id="cname"></a>

سجل DNS يجعل اسمًا مرادفًا لاسم آخر. مفيد عند توجيه نطاق فرعي إلى خدمة.

**في مرسى:** قد يُستخدم كبديل للتحقق أو التوجيه.

### TLS <a id="tls"></a>

بروتوكول تشفير اتصالات الشبكة. HTTPS هو HTTP داخل TLS.

**في مرسى:** كل نطاق عام يجب أن يعمل عبر TLS، وتدير Caddy الشهادات.

### ACME <a id="acme"></a>

بروتوكول آلي لإصدار الشهادات، يستخدمه Let’s Encrypt وغيره. يتطلب عادةً الوصول إلى المنفذ 80 أو DNS.

**في مرسى:** Caddy يستخدم ACME، ويُستخدم مركز اختبار في الاختبارات.

### الشهادة — Certificate <a id="certificate"></a>

ملف يثبت هوية الموقع ويُمكّن التشفير. لها مدة صلاحية وتجديد تلقائي.

**في مرسى:** لا تحتفظ مرسى بمفاتيح الشهادة الخاصة؛ Caddy يديرها.

### إنهاء TLS — TLS Termination <a id="tls-termination"></a>

فك تشفير HTTPS عند الحافة، ثم تمرير الطلب عبر شبكة داخلية. هذا ما يفعله Caddy.

**في مرسى:** الحركة الداخلية بين Caddy والتطبيق ليست TLS افتراضيًا؛ الشبكة معزولة.

### المنفذ — Port <a id="port"></a>

رقم يحدد خدمة على جهاز، مثل 80 لـHTTP و443 لـHTTPS. التطبيق يستمع على منفذ داخلي.

**في مرسى:** لا تُنشر منافذ التطبيقات على المضيف؛ Caddy يصل إليها عبر الشبكة.

### مقبس Unix — Unix Socket <a id="unix-socket"></a>

قناة اتصال محلية بين عمليات على نفس الجهاز، تظهر كملف بصلاحيات. لا تُعرَض على الشبكة.

**في مرسى:** إدارة Caddy وDocker تتم عبر مقابس محلية، لا منافذ TCP عامة.

### مقبس إدارة Caddy — Caddy Admin Socket <a id="caddy-admin-socket"></a>

المقبس المحلي الذي يسمح لخادم مرسى بتغيير مسارات Caddy وشهاداتها دون فتح منفذ إدارة على الشبكة.

**في مرسى:** يقع في `/run/marsa/caddy/admin.sock`، بصلاحيات `0660` ومجلد `0700`. لا يوجد مستمع TCP على المنفذ `2019`.

### الاسترجاع المحلي — Loopback <a id="loopback"></a>

عنوان يشير إلى الجهاز نفسه، مثل `127.0.0.1`. لا يُقصد به الوصول من الإنترنت.

**في مرسى:** تُستخدم منافذ loopback لأغراض داخلية محدودة، وليس لنشر التطبيق.

### Wildcard <a id="wildcard"></a>

اسم نطاق يطابق نطاقات فرعية متعددة، مثل `*.example.com`. مفيد لكنه يزيد تعقيد الشهادات والأمان.

**في مرسى:** غير مدعوم في 0.1.

### الجدار الناري — Firewall <a id="firewall"></a>

قواعد تتحكم في حركة الشبكة الداخلة والخارجة. يجب أن يسمح فقط بالمنافذ اللازمة.

**في مرسى:** 80 و443 للعامة، والبقية داخلية.

## 5. البيانات والحالة <a id="data-state"></a>

### PostgreSQL <a id="postgresql"></a>

قاعدة بيانات علائقية مفتوحة المصدر. تدعم المعاملات والقيود والاستعلامات المعقدة.

**في مرسى:** الحالة الدائمة الوحيدة المطلوبة. تخزّن المشاريع والنشرات والأسرار المشفرة والتدقيق والطابور.

### المخطط — Schema <a id="schema"></a>

تعريف بنية البيانات: الجداول، الأعمدة، الفهارس، والقيود.

**في مرسى:** الهجرات تغيّر المخطط بشكل صريح، وبدون ترحيل تلقائي عند بدء التشغيل.

### الهجرة — Migration <a id="migration"></a>

تغيير مُدار في مخطط قاعدة البيانات. يجب أن يكون قابلًا للتطبيق بأمان أثناء الترقية.

**في مرسى:** تُستخدم هجرات expand/contract، وتُختبر على قاعدة مليئة بالبيانات.

### وقت قاعدة البيانات — Database Time <a id="database-time"></a>

استخدام ساعة قاعدة البيانات بدل ساعة التطبيق لقياس المهلات والترتيب.

**في مرسى:** عقود الإيجار والترتيب يفضّلان وقت قاعدة البيانات لتقليل انحراف الساعات.

### UTC <a id="utc"></a>

توقيت عالمي موحد بلا تغيير موسمي. يُستخدم لتخزين الأوقات.

**في مرسى:** كل الأوقات المحفوظة UTC، وتُعرض محليًا في الواجهة.

### عقد الإيجار — Lease <a id="lease"></a>

حق مؤقت لعامل بأن ينفّذ مهمة. يجب تجديده عبر نبضة قلب؛ إذا انتهى، يمكن لعامل آخر المتابعة.

**في مرسى:** الافتراضي 60 ثانية، مع نبضة كل 15 ثانية.

### العامل — Worker <a id="worker"></a>

عملية في الخلفية تنفّذ النشر خطوة بخطوة. ليست واجهة المستخدم، لكنها القلب التنفيذي.

**في مرسى:** جزء من خادم ASP.NET Core، ويستأنف العمل بعد إعادة التشغيل.

### نبضة القلب — Heartbeat <a id="heartbeat"></a>

إشارة دورية تؤكد أن العامل ما زال حيًا. تمنع عاملًا ميتًا من الاحتفاظ بالمهمة إلى الأبد.

**في مرسى:** كل 15 ثانية، وتُجدّد الإيجار.

### صندوق الصادر — Outbox <a id="outbox"></a>

نمط يحفظ الحدث في قاعدة البيانات مع تغيير الحالة في نفس المعاملة، ثم يُسلّمه لاحقًا. يمنع فقدان الأحداث أو إرسالها مرتين.

**في مرسى:** يستخدم لنشر الأحداث إلى SignalR والطابور بعد commit.

### إعادة المحاولة الآمنة — Idempotency <a id="idempotency"></a>

خاصية تجعل تكرار الطلب يعطي نفس النتيجة دون أثر إضافي. تُستخدم مع مفاتيح فريدة.

**في مرسى:** نفس مفتاح Idempotency يعيد النشر الأصلي بدل إنشاء نشر ثانٍ.

### UUIDv7 <a id="uuidv7"></a>

معرّف فريد يمكن ترتيبه زمنيًا، ما يحسّن أداء الفهارس مقارنة بـUUID العشوائي.

**في مرسى:** يُستخدم لمعرّفات الكيانات الجديدة.

### فهرس فريد جزئي — Partial Unique Index <a id="partial-unique-index"></a>

فهرس يفرض التفرّد على صفوف تحقق شرطًا فقط، مثل النشرات النشطة.

**في مرسى:** يضمن نشرًا نشطًا واحدًا لكل بيئة حتى تحت التزامن.

### النسخ الاحتياطي — Backup <a id="backup"></a>

نسخة من البيانات يمكن استعادتها بعد فقدان أو تلف. ليست نسخة من الكود فقط.

**في مرسى:** `pg_dump` مع نسخة منفصلة من المفتاح الرئيسي.

### الاستعادة — Restore <a id="restore"></a>

إعادة البيانات من نسخة احتياطية إلى نظام يعمل. يجب اختبارها، لا مجرد توثيقها.

**في مرسى:** تمرين استعادة قبل الإصدار، ويشمل الأسرار والمفتاح الرئيسي.

### مدة الاحتفاظ — Retention <a id="retention"></a>

المدة التي تُحفظ فيها السجلات أو الصور أو البيانات قبل حذفها. يجب أن تكون محدودة ومفهومة.

**في مرسى:** 30 يومًا لسجلات النشر، 14 يومًا لسجلات التطبيق، سنة للتدقيق افتراضيًا.

### حالة متدهورة — Degraded <a id="degraded"></a>

النظام يعمل جزئيًا لكن مكوّنًا مهمًا مفقود أو غير سليم. تختلف عن الفشل الكامل.

**في مرسى:** `/health/degraded` يعرض المكوّنات الاختيارية والتحذيرات.

## 6. الأمان والهوية <a id="security-identity"></a>

### المصادقة والتفويض — Authentication and Authorization <a id="authn-authz"></a>

المصادقة تجيب „من أنت؟“، والتفويض يجيب „ماذا يحق لك أن تفعل؟“. لا يكفي إثبات الهوية وحدها.

**في مرسى:** الجلسات ورموز Marsa PAT تثبت الهوية، والأدوار والصلاحيات تحدد الأفعال.

### الجلسة — Session <a id="session"></a>

حالة تسجيل دخول محفوظة بين الطلبات، غالبًا عبر كوكي. يجب أن تنتهي عند تسجيل الخروج.

**في مرسى:** جلسات الواجهة عبر كوكي آمن، وتُبطل من الخادم عند الخروج.

### كوكي — Cookie <a id="cookie"></a>

قطعة بيانات صغيرة يرسلها الخادم إلى المتصفح ويعيدها في الطلبات اللاحقة. تُستخدم للجلسات.

**في مرسى:** `HttpOnly` و`Secure` في الإنتاج و`SameSite=Lax`.

### CSRF <a id="csrf"></a>

اختصار Cross-Site Request Forgery: جعل متصفح مستخدم مسجّل ينفّذ طلبًا غير مقصود إلى موقع آخر.

**في مرسى:** عمليات التغيير عبر الكوكي تتطلب رمز antiforgery.

### الأدوار — RBAC <a id="rbac"></a>

اختصار Role-Based Access Control: منح الصلاحيات حسب الدور بدل المستخدم الفردي.

**في مرسى:** مالك، مدير، مطوّر، مشاهد، ولكل دور مصفوفة صلاحيات.

### المؤسسة — Organization <a id="organization"></a>

الوحدة التي تملك المشاريع والأعضاء والموارد. في 0.1، توجد مؤسسة واحدة لكل تثبيت.

**في مرسى:** كل صف تابع للمؤسسة يحمل `organization_id` حتى لو كان هناك مؤسسة واحدة الآن.

### المستأجر — Tenant <a id="tenant"></a>

جهة معزولة منطقيًا عن غيرها داخل النظام. في مرسى متعدد المؤسسات مستقبلًا، كل مؤسسة مستأجر.

**في مرسى:** الاستعلامات تحصر الوصول في المؤسسة الحالية، واختبارات العزل تمنع التسرب.

### التدقيق — Audit <a id="audit"></a>

سجل أحداث حساسة: من فعل ماذا، على أي مورد، ومتى، دون قيم سرية. يجب أن يكون غير قابل للتعديل من التطبيق.

**في مرسى:** يغطي التهيئة، الدخول، المشاريع، المصادر، النشر، التراجع، الأسرار، النطاقات، والرموز.

### السر — Secret <a id="secret"></a>

قيمة حساسة مثل كلمة مرور أو مفتاح API. لا يجب أن تظهر في السجلات أو واجهات القوائم.

**في مرسى:** يُخزَّن مشفرًا، ويُحقن عند إنشاء الحاوية فقط.

### التشفير المغلف — Envelope Encryption <a id="envelope-encryption"></a>

تشفير البيانات بمفتاح بيانات، ثم تشفير مفتاح البيانات بمفتاح رئيسي. يفصل المفتاح طويل الأمد عن كل سر.

**في مرسى:** يسمح بتدوير المفاتيح دون إعادة تشفير كل شيء دفعة واحدة.

### المفتاح الرئيسي — Master Key <a id="master-key"></a>

المفتاح الأعلى الذي يحمي مفاتيح البيانات. يجب أن يبقى خارج قاعدة البيانات وخارج الصورة.

**في مرسى:** فقدانه يعني فقدان القدرة على فك الأسرار؛ يجب نسخه احتياطيًا منفصلًا.

### AES-256-GCM <a id="aes-gcm"></a>

خوارزمية تشفير متماثل توفر السرية والتحقق من السلامة. تستخدم nonce فريدًا لكل عملية.

**في مرسى:** أساس التشفير المغلف، مع تسجيل إصدار المفتاح.

### التنقية — Redaction <a id="redaction"></a>

إزالة أو إخفاء القيم الحساسة قبل تخزين السجلات أو عرضها أو تصديرها.

**في مرسى:** تُطبَّق قبل الحفظ والبث، لا عند العرض فقط.

### قيمة اختبار التسرب — Secret Canary <a id="secret-canary"></a>

قيمة وهمية تشبه السر تُزرع في الاختبار للتأكد من أنها لا تظهر في أي مخرج.

**في مرسى:** اختبار canary يفشل الإصدار إذا ظهرت القيمة في السجلات أو الأحداث أو API.

### مقبس Docker — Docker Socket <a id="docker-socket"></a>

ملف محلي مثل `/var/run/docker.sock` يسمح بإدارة Docker عبر API. من يملكه يستطيع إنشاء حاويات privileged وتركيب ملفات المضيف.

**في مرسى:** يبقى لدى خادم مرسى فقط. لا تحصل عليه الحاويات ولا عمليات البناء ولا تطبيقات المستخدمين.

### الجذر المكافئ — Root-equivalent <a id="root-equivalent"></a>

صلاحية تعادل root فعليًا حتى لو لم تحمل الاسم. الوصول إلى Docker socket مثال عليها.

**في مرسى:** يُوثَّق هذا الخطر بوضوح ولا يُخفى.

### الامتياز — Privileged <a id="privileged"></a>

وضع حاوية يمنحها صلاحيات واسعة على المضيف. يلغي الكثير من العزل.

**في مرسى:** مرفوض للحاويات والبناءات.

### تركيب المضيف — Host Mount <a id="host-mount"></a>

ربط مجلد من نظام المضيف داخل الحاوية. قد يسمح بقراءة أو تعديل ملفات الخادم.

**في مرسى:** مرفوض للمستخدمين؛ لا تُركَّب مسارات المضيف في التطبيقات.

### أقل صلاحية — Least Privilege <a id="least-privilege"></a>

منح كل مكوّن أقل صلاحيات يحتاجها فقط.

**في مرسى:** الحاويات بلا Docker socket، وCaddy بلا Docker، والـworker بصلاحيات محددة.

### حد المعدل — Rate Limit <a id="rate-limit"></a>

تقييد عدد الطلبات في فترة زمنية لمنع الإساءة أو هجمات الحرمان.

**في مرسى:** يشمل الدخول، التهيئة، النشر، webhooks، وبث السجلات.

### قائمة مكونات البرمجيات — SBOM <a id="sbom"></a>

اختصار Software Bill of Materials: جرد بالمكونات والنسخ والتراخيص في الإصدار.

**في مرسى:** مطلوب في مرشح الإصدار، مع فحص التراخيص.

### سلسلة التوريد — Supply Chain <a id="supply-chain"></a>

كل ما يدخل في بناء البرنامج: الاعتماديات، الصور الأساسية، الأدوات، والمصادر.

**في مرسى:** تُفحص التراخيص والثغرات، وتُثبَّت الصور بالبصمة.

### الترخيص — License <a id="license"></a>

شروط قانونية لاستخدام الكود وإعادة توزيعه. ليست مجرد ملف في المستودع.

## 7. الواجهات واللغات <a id="interfaces-languages"></a>

### API <a id="api"></a>

اختصار Application Programming Interface: عقد برمجي يسمح لبرنامج بالتواصل مع آخر.

**في مرسى:** `/api/v1` هو العقد العام للواجهة وCLI.

### REST <a id="rest"></a>

أسلوب لتصميم واجهات HTTP حول الموارد والأفعال القياسية.

**في مرسى:** نقاط نهاية RESTية تحت `/api/v1`، مع ProblemDetails للأخطاء.

### نقطة نهاية — Endpoint <a id="endpoint"></a>

عنوان وطريقة HTTP يمثلان عملية، مثل `POST /api/v1/projects`.

**في مرسى:** كل نقطة تمر عبر التفويض والتحقق.

### OpenAPI <a id="openapi"></a>

وصف آلي لواجهة HTTP، يشمل المسارات والمخططات والأخطاء. يمكن توليد عملاء منه.

**في مرسى:** يُولَّد من الكود، ويُستخدم لتوليد عميل CLI واختبار العقد.

### ProblemDetails <a id="problemdetails"></a>

صيغة قياسية لوصف أخطاء HTTP: النوع، العنوان، الحالة، والتفاصيل.

**في مرسى:** تضيف رمزًا ثابتًا و`traceId` ورسالة آمنة.

### CLI <a id="cli"></a>

اختصار Command-Line Interface: واجهة سطر أوامر. مناسبة للأتمتة والسيناريوهات غير التفاعلية.

**في مرسى:** `marsa` مع أوامر مثل `login` و`deploy` و`status` و`logs`.

### SignalR <a id="signalr"></a>

مكتبة .NET للاتصال ثنائي الاتجاه في الوقت الحقيقي. تُستخدم لتحديث الحالة والسجلات مباشرة.

**في مرسى:** يبث أحداث النشر بعد commit، ويدعم إعادة التشغيل من آخر تسلسل.

### Razor Components <a id="razor"></a>

طريقة ASP.NET Core لبناء واجهات باستخدام C# وHTML، مع إمكانية تفاعل من الخادم.

**في مرسى:** الواجهة server-rendered، بلا SPA أو بناء Node منفصل.

### العرض من الخادم — SSR <a id="ssr"></a>

اختصار Server-Side Rendering: توليد HTML على الخادم لكل طلب أو صفحة.

**في مرسى:** يقلل التعقيد ويجعل الصفحات قابلة للاستخدام بسرعة.

### تطبيق صفحة واحدة — SPA <a id="spa"></a>

تطبيق ويب يحمّل صفحة واحدة ثم يتفاعل عبر JavaScript. يحتاج بناء منفصلًا وغالبًا API منفصلًا.

**في مرسى:** غير مستخدم في 0.1.

### التدويل — i18n <a id="i18n"></a>

تصميم البرنامج لدعم عدة لغات وثقافات: النصوص، التواريخ، الأرقام، والاتجاه.

**في مرسى:** العربية والإنجليزية جزء من معايير القبول.

### من اليمين إلى اليسار — RTL <a id="rtl"></a>

اتجاه كتابة العربية والعبرية. لا يعني „عكس كل شيء“؛ السجلات والكود تبقى LTR.

**في مرسى:** يُختبر على عرض 360 و1280 بكسل.

### إمكانية الوصول — A11y <a id="a11y"></a>

اختصار Accessibility: جعل الواجهة قابلة للاستخدام بلوحة المفاتيح وقارئ الشاشة وبتناقض كافٍ.

**في مرسى:** تسميات، تركيز واضح، ملخص أخطاء، وعدم الاعتماد على اللون وحده.

### اللغة الإنجليزية — LTR <a id="ltr"></a>

اتجاه الكتابة من اليسار إلى اليمين، المستخدم في الإنجليزية والكود والسجلات.

**في مرسى:** تبقى كتل الكود والسجلات LTR حتى داخل واجهة عربية.

## 8. تقنيات .NET <a id="dotnet"></a>

### .NET <a id="dotnet-platform"></a>

منصة تطوير من Microsoft لبناء تطبيقات ويب وسطح مكتب وخدمات. تشمل وقت تشغيل ومكتبات وأدوات.

لغة برمجة أساسية لمنصة .NET، حديثة ومتعددة الأنماط.

### ASP.NET Core <a id="aspnet"></a>

إطار لبناء تطبيقات ويب وواجهات API على .NET. يشمل التوجيه، التفويض، والحقن.

**في مرسى:** خادم مرسى هو تطبيق ASP.NET Core.

اختصار Entity Framework Core: إطار لربط كائنات C# بقاعدة بيانات علائقية.

### حقن التبعية — DI <a id="di"></a>

نمط يمرر المكوّنات التي يحتاجها كائن بدل أن ينشئها بنفسه. يسهّل الاختبار والاستبدال.

### Minimal APIs <a id="minimal-api"></a>

أسلوب مختصر في ASP.NET Core لتعريف نقاط النهاية دون controllers ثقيلة.

**في مرسى:** تُستخدم لتعريف `/api/v1` مع ربط رفيع.

### خدمة خلفية — BackgroundService <a id="background-service"></a>

فئة في .NET لتشغيل عمل مستمر في الخلفية داخل التطبيق.

**في مرسى:** العامل الذي ينفّذ النشر.

### الكتلة الواحدة — Monolith <a id="monolith"></a>

تطبيق واحد يحتوي كل المكوّنات، بدل خدمات منفصلة. أسهل في النشر لكنه قد يصبح متشابكًا.

**في مرسى:** خادم واحد، لا شبكة خدمات.

### الكتلة المعيارية — Modular Monolith <a id="modular-monolith"></a>

كتلة واحدة ذات حدود وحدات واضحة، مثل Identity وProjects وDeployments، مع قواعد اعتماد.

**في مرسى:** الشكل المعماري الأساسي: خادم واحد، وحدات منفصلة منطقيًا.

### حل .NET — Solution <a id="solution"></a>

ملف يجمع مشاريع .NET المترابطة، مثل `Marsa.sln`.

**في مرسى:** يحدد مشاريع Domain وApplication وInfrastructure وServer وCLI والاختبارات.

## 9. إدارة المشروع <a id="project-management"></a>

### الغرفة النظيفة — Clean-room <a id="clean-room"></a>

عملية لبناء منتج بعد دراسة سلوك منتج آخر، مع كتابة التعبير والكود من الصفر. ليست نسخًا ولا ترجمة حرفية.

**في مرسى:** السلوك والتصميم مفهومان، لكن لا يُنسخ كود أو نثر أو مخططات من Openship.

### سجل قرار معماري — ADR <a id="adr"></a>

مستند قصير يشرح قرارًا معماريًا مهمًا: السياق، القرار، العواقب، والبدائل المرفوضة.

**في مرسى:** يوجد 20 ADR للقرارات الأساسية.

### متطلب — Requirement (Requirements) <a id="requirement"></a>

وصف لسلوك أو قيد يجب أن يحققه المنتج، مع معرّف ومعايير قبول.

**في مرسى:** المتطلبات الوظيفية تبدأ بـ`FR-`، وغير الوظيفية بـ`NFR-`.

### MUST وSHOULD وCOULD وOUT <a id="must-should"></a>

تصنيفات أولوية:
- **MUST:** مطلوب للإصدار.
- **SHOULD:** متوقع لكن يمكن تأجيله بقرار.
- **COULD:** اختياري.
- **OUT:** خارج النطاق.

**في مرسى:** 151 صفًا في مستند المتطلبات: 102 MUST و11 SHOULD و1 COULD و7 OUT، إضافة إلى 30 NFR. المُلزم في 0.1 هو 132 متطلبًا (102 MUST وظيفية + 30 NFR).

### الخارطة — Roadmap <a id="roadmap"></a>

خطة مرحلية لبناء المنتج، تربط الأهداف بالميلستونات وليس بالتواريخ.

**في مرسى:** M0 إلى M6، وكل مرحلة شريحة رأسية قابلة للعرض.

### قائمة الأعمال — Backlog <a id="backlog"></a>

قائمة المهام المرتبة التي لم تُنجز بعد.

**في مرسى:** 39 مهمة تغطي المتطلبات والقصص، مع اعتماديات وأحجام.

### المهمة — Issue <a id="issue"></a>

قطعة عمل محددة لها سياق ومعايير قبول واعتماديات.

**في مرسى:** كل مهمة تشير إلى المتطلبات والـADR والاختبارات المتوقعة.

### الشريحة الرأسية — Vertical Slice <a id="vertical-slice"></a>

جزء صغير يكمل مسارًا من الواجهة إلى قاعدة البيانات والاختبار، بدل طبقة أفقية فقط.

**في مرسى:** كل ميلستون شريحة رأسية، وكل مهمة تُنجز سلوكًا يمكن اختباره.

### الإصدار الدلالي — SemVer <a id="semver"></a>

نظام `major.minor.patch` حيث يزيد major عند تغيير كاسر، وminor عند ميزة، وpatch عند إصلاح.

**في مرسى:** قبل 1.0 قد تُضاف ميزات، لكن التغييرات الكاسرة تُوثَّق.

### التكامل والتسليم المستمر — CI/CD <a id="ci-cd"></a>

CI: بناء واختبار تلقائي عند كل تغيير. CD: تسليم أو نشر تلقائي بعد النجاح.

**في مرسى:** CI يفحص الوثائق والـbacklog والبناء، ولا ينشر الإنتاج تلقائيًا.

### تعريف الإنجاز — Definition of Done <a id="definition-of-done"></a>

قائمة شروط تعني أن المهمة اكتملت فعلًا: الاختبارات، الوثائق، الأمان، العربية، والمراجعة.

**في مرسى:** لا تُعد المهمة منتهية بمجرد „أنها تعمل على جهاز المطوّر“.

### اختبار E2E <a id="e2e"></a>

اختبار يشغّل مسارًا كاملًا من واجهة المستخدم إلى قاعدة البيانات والخدمات الحقيقية.

**في مرسى:** نشر ناجح، فشل بناء، فشل صحة، تراجع، وإلغاء على بيئة قابلة للتخلص منها.

### اختبار الوحدة — Unit Test <a id="unit-test"></a>

اختبار سريع لدالة أو كائن صغير بمعزل عن الخارج.

**في مرسى:** يغطي قواعد المجال وآلة الحالة.

### اختبار التكامل — Integration Test <a id="integration-test"></a>

اختبار يتحقق من تكامل مكوّنات حقيقية مثل قاعدة البيانات وDocker.

**في مرسى:** يستخدم Testcontainers وبيانات معزولة.

### المراجعة — Code Review <a id="code-review"></a>

فحص تغيير قبل دمجه: الصحة، الأمان، الاختبارات، والاتساق مع الوثائق.

**في مرسى:** قائمة المراجعة تمنع „نجاحًا“ بلا دليل.

## 10. التشغيل والمراقبة <a id="operations"></a>

### الفحص الأولي — Preflight <a id="preflight"></a>

**في مرسى:** يعطي لكل فحص نجاحًا أو فشلًا مع تلميح إصلاح.

قدرة المشغّل على فهم ما يحدث من الخارج عبر السجلات والمقاييس والآثار.

**في مرسى:** كل نشر له خط زمني، وكل طلب له معرّف ارتباط.

### السجل — Log <a id="log"></a>

رسالة نصية موثقة بوقتها ومصدرها. قد تكون سجل تطبيق أو سجل نشر.

**في مرسى:** تُنقّى من الأسرار قبل الحفظ، وتبقى بعد إعادة التحميل.

### المقياس — Metric <a id="metric"></a>

قيمة رقمية تُقاس دوريًا، مثل عدد النشرات أو مدة المرحلة.

### الأثر — Trace <a id="trace"></a>

سجل لمسار طلب عبر مكوّنات متعددة، يربط الأجزاء بمعرّف واحد.

**في مرسى:** OpenTelemetry اختياري، وليس شرطًا لتشغيل صحي.

### OpenTelemetry — OTLP <a id="opentelemetry"></a>

معيار مفتوح لجمع المقاييس والآثار والسجلات وتصديرها.

**في مرسى:** التصدير اختياري ومُعطّل افتراضيًا؛ لا تلمترية صامتة.

### التشخيص — Diagnostics <a id="diagnostics"></a>

معلومات تساعد على فهم مشكلة: حالة المكوّنات، القرص، الإصدار، والخطوة التالية، دون كشف أسرار.

**في مرسى:** صفحة تشخيص منقّحة، وليست طرفية تفاعلية.

### دليل التشغيل — Runbook <a id="runbook"></a>

إجراء مكتوب لحالة تشغيلية، مثل التثبيت أو الاستعادة أو تدوير المفتاح.

**في مرسى:** يُختبر بواسطة شخص لم يكتبه.

### اتفاقية مستوى الخدمة — SLA <a id="sla"></a>

التزام رسمي بزمن الاستجابة أو التوفر. مرسى 0.1 لا يقدّم SLA.

**في مرسى:** الأهداف أداء وتجربة، وليست وعودًا تعاقدية.

### مخرج الإصدار — Artifact <a id="artifact"></a>

ملف أو حزمة قابلة للتوزيع: صورة، ملف CLI، حزمة هجرة، أو SBOM.

**في مرسى:** الإصدار يحتوي صورة متعددة المعماريات، CLI، هجرة، قوالب، وبصمات.

### الخادم — Server <a id="server"></a>

جهاز أو عملية تخدم طلبات. قد يعني العتاد أو البرنامج.

**في مرسى:** خادم Linux واحد، وعملية `Marsa.Server` واحدة.

### الخادم الافتراضي — VPS <a id="vps"></a>

خادم افتراضي خاص تستأجره من مزوّد. مناسب للتثبيت الصغير.

**في مرسى:** الحد الأدنى المقترح 2 vCPU و4 GB RAM و20 GB قرص.

### Linux <a id="linux"></a>

نظام تشغيل مفتوح المصدر. مرسى 0.1 يدعم x86_64 وarm64 فقط.

**في مرسى:** لا دعم لـWindows أو macOS كمضيف.

### الشبكة — Network <a id="network"></a>

ربط بين حاويات أو أجهزة. العزل الشبكي يمنع تطبيقًا من رؤية آخر بلا إذن.

**في مرسى:** شبكة تحكم، وشبكة لكل مشروع.

### شبكة المشروع — Project Network <a id="project-network"></a>

شبكة Docker خاصة بمشروع، تصل الحاوية بـCaddy دون تعريض منفذ على المضيف.

**في مرسى:** لكل مشروع شبكة، وCaddy فقط يتصل بعدة شبكات.

### عنوان IP <a id="ip-address"></a>

معرّف رقمي لجهاز على شبكة. قد يكون عامًا أو خاصًا.

**في مرسى:** العناوين الخاصة والمحلية تُحجب في فحص SSRF.

### التشفير — Encryption <a id="encryption"></a>

تحويل بيانات إلى شكل غير مفهوم بدون مفتاح. لا يحمي من فقدان المفتاح.

**في مرسى:** الأسرار مشفرة في قاعدة البيانات، والاتصال العام عبر TLS.

### النص الواضح — Plaintext <a id="plaintext"></a>

البيانات قبل التشفير أو بعد فك التشفير. يجب ألا تُخزَّن أو تُسجَّل.

**في مرسى:** النص الواضح للسر موجود فقط عند إنشاء الحاوية.

## 11. حالات النشر <a id="deployment-states"></a>

هذه الحالات الجزء الأهم لفهم „أين وصل النشر؟“.

| الحالة | المعنى | ماذا يعني للمستخدم؟ |
|---|---|---|
| **queued** <a id="queued"></a> | تم قبول النشر وينتظر عاملًا | لا تفعل شيئًا؛ سيبدأ قريبًا |
| **preparing** <a id="preparing"></a> | تجهيز المصدر والتحقق من اللقطة | تحقق من الأخطاء إن طال الوقت |
| **building** <a id="building"></a> | بناء صورة التطبيق | راقب السجلات |
| **deploying** <a id="deploying"></a> | إنشاء الحاوية وتشغيلها | قد يكون خطأ منفذ أو بدء |
| **health_checking** <a id="health-checking"></a> | فحص الصحة والاستقرار | لا حركة جديدة بعد |
| **routing** <a id="routing"></a> | تحويل النطاق إلى الإصدار الجديد | لحظات حاسمة؛ لا إلغاء |
| **succeeded** <a id="succeeded"></a> | نجاح كامل | الإصدار يخدم |
| **succeeded_with_warnings** <a id="succeeded-with-warnings-state"></a> | نجاح مع تحذير | اقرأ التحذير وأصلحه |
| **action_required** <a id="action-required-state"></a> | توقف آمن يحتاج قرارًا | راجع السبب ثم أعد المحاولة أو تراجع |
| **failed** <a id="failed"></a> | فشل نهائي | راجع الخطوة والرمز |
| **cancelled** <a id="cancelled"></a> | أُلغي بأمان | يمكنك إعادة المحاولة |

### الانتقالات الممنوعة

- لا رجوع من `building` إلى `queued`.
- لا تعديل بعد `succeeded` أو `failed`.
- لا إلغاء أثناء `routing`.
- لا تراجع تلقائي من `failed`.

**في مرسى:** فحص العلامة غير مكتمل، ويُعد بوابة إطلاق.

### اسم النطاق — Domain Name <a id="domain-name"></a>

عنوان مقروء على الإنترنت، مثل `example.com`. ملكيته تنتهي إذا لم تُجدد.

**في مرسى:** لا نطاق عام مملوك بعد، لذلك تُستخدم روابط نسبية و`urn:marsa:*`.

### URN <a id="urn"></a>

معرّف دائم لا يعتمد على موقع ويب. في مرسى يُستخدم مثل `urn:marsa:error:...`.

**لماذا:** يمنع الاعتماد على نطاق غير مملوك في العقود.

### المصدر المفتوح — Open Source <a id="open-source"></a>

نموذج توزيع يمنح صلاحيات قراءة وتعديل وتوزيع الكود وفق الترخيص.

**في مرسى:** الهدف Apache-2.0، لكن الترخيص ما زال مقترحًا.

### المستودع الأحادي — Monorepo <a id="monorepo"></a>

مستودع واحد يضم مشاريع متعددة. يحتاج إلى مسار مشروع صريح حتى لا يخمّن مرسى.

**في مرسى:** الاكتشاف لا يتجول عشوائيًا؛ يحتاج جذرًا صريحًا أو Dockerfile.

## 13. مصطلحات سريعة إضافية

### التهيئة — Setup <a id="setup"></a>

الخطوات الأولى لإنشاء نسخة مرسى: رمز لمرة واحدة، مالك، مؤسسة.

**في مرسى:** لا تُعاد التهيئة بعد اكتمالها.

### رمز التهيئة — Setup Token <a id="setup-token"></a>

رمز عشوائي يثبت أن من يفتح الصفحة يملك وصولًا إلى الخادم. يُعرض مرة واحدة.

**في مرسى:** بدونه لا يمكن إنشاء أول مالك.

### معدل الفشل — Failure Rate <a id="failure-rate"></a>

نسبة المحاولات الفاشلة إلى الإجمالي. مقياس مفيد لكنه لا يفسر السبب وحده.

**في مرسى:** تُقاس مع سبب الفشل، لا كرقم مجرد.

### السعة — Capacity <a id="capacity"></a>

الحد الأقصى لما يستطيع النظام التعامل معه من مشاريع أو نشرات أو مستخدمين.

**في مرسى:** أهداف 0.1 هي 100 مشروع و500 خدمة و4 نشرات متزامنة و20 مستخدمًا.

### التوسع الأفقي — Horizontal Scaling <a id="horizontal-scaling"></a>

إضافة نسخ أو خوادم أكثر لتوزيع الحمل، بدل تكبير خادم واحد.

**في مرسى:** خارج 0.1؛ التصميم يبدأ رأسيًا على مضيف واحد.

### القيد — Constraint <a id="constraint"></a>

قاعدة تفرضها قاعدة البيانات أو الكود، مثل عدم وجود نشرين نشطين.

**في مرسى:** القيود هي الضمان الأخير، وليست مجرد تحقق في الواجهة.

### المعاملة — Transaction <a id="transaction"></a>

مجموعة عمليات تُنفّذ كوحدة: إما تنجح كلها أو تفشل كلها.

**في مرسى:** القبول واللقطة والحدث تُكتب في معاملة واحدة.

### القفل — Lock <a id="lock"></a>

آلية تمنع تعديلين متزامنين لنفس المورد. قد يكون صفًا في قاعدة البيانات أو قفلًا في الذاكرة.

**في مرسى:** قفل صف البيئة يمنع نشرين متوازيين.

### التزامن — Concurrency <a id="concurrency"></a>

تنفيذ عدة عمليات في نفس الوقت. يزيد الإنتاجية لكنه يخلق سباقات.

**في مرسى:** اختبارات التزامن تثبت عدم إنشاء نشرين نشطين.

### السباق — Race Condition <a id="race-condition"></a>

خطأ يحدث عندما تعتمد نتيجة العملية على ترتيب غير مضمون بين عمليات متزامنة.

**في مرسى:** القيد الفريد الجزئي والقفل يمنعان سباق القبول.

### الانهيار — Crash <a id="crash"></a>

توقف غير متوقع لعملية. يجب أن يكون النظام قادرًا على الاستعادة.

**في مرسى:** قتل العامل أثناء البناء مُختبر؛ الإيجار ينتهي ويستأنف عامل آخر.

### الاستئناف — Resume <a id="resume"></a>

متابعة عمل بعد توقف، بناءً على حالة محفوظة.

**في مرسى:** الخطوات idempotent، فيمكن إعادة تنفيذها بأمان.

### التجربة — Staging <a id="staging"></a>

بيئة قريبة من الإنتاج للاختبار. ليست بديلًا عن الاختبارات الآلية.

**في مرسى:** مركز شهادات اختبار وبيئة E2E، لا وعود بإنتاج مطابق.

### الإنتاج — Production <a id="production"></a>

البيئة التي يستخدمها المستخدمون الحقيقيون. تتطلب أعلى درجات الحذر.

**في مرسى:** لا ترحيل تلقائي، لا تراجع تلقائي، ولا كلمات مرور افتراضية.

### الحادث — Incident <a id="incident"></a>

حدث يؤثر على الخدمة ويحتاج استجابة. يختلف عن خطأ بناء عادي.

**في مرسى:** دليل التشخيص والتدقيق يساعدان على فهم الأثر.

### السبب الجذري — Root Cause <a id="root-cause"></a>

السبب الأساسي للمشكلة، لا مجرد عرضها. إصلاحه يمنع التكرار.

**في مرسى:** كل فشل له رمز ثابت وخطوة، لتسهيل التحليل.

### الدليل — Evidence <a id="evidence"></a>

معلومة تثبت أن خطوة نجحت أو فشلت: سجل، نتيجة فحص، أو بصمة.

**في مرسى:** لا يُعلن النجاح بلا دليل قابل للفحص.

### مسار مقترح للمبتدئ

```text
Git وcommit وpush
  -> Docker وimage وcontainer
  -> DNS وTLS وCaddy
  -> deployment وsnapshot وhealth check
  -> rollback وaudit وsecrets
  -> state machine وlease وreconciliation
```

هذا المسار يبني الفهم تدريجيًا: أولًا كيف يصل الكود، ثم كيف يعمل، ثم كيف نثق به ونستعيده عند الفشل.
